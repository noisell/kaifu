# Технический статус

Я проверил backend из коммита `c616bbb` (`forgotten improvements`) и frontend из `9259168`. Дата проверки: 5 ноября 2026 года. Я самостоятельно разработал весь проект; аудитория проекта составляла 10 000 пользователей.

## Что изменилось после восстановления backend

Все пять групп роутеров подключены: auth, user, system, lottery и admin. Появились административная авторизация, API пользователей и экономики, билеты, выигрыши, задания, рефералы, статистика, Celery и RabbitMQ consumer. ## Оставшиеся ограничения

### Восстановление схемы и начальных данных

- Новая история миграций заменяет старую: `c44d01bdd5d6` не является продолжением прежних ревизий. Нельзя применять её поверх старой базы без отдельного плана миграции. Проверка выполнена на новой базе.
- В модели `Task` есть `sub_inst`, но в миграции столбца нет. Это воспроизводимо ломает `/user/task`.
- Enum `systemnames` не содержит всех значений модели: отсутствуют `course_stars`, `price_gold_ticket_stars`, `stars` и параметры `investment_*`. В `wintype` нет `referrer`, присутствующего в модели.
- Миграция создаёт таблицы, но не заполняет банк, счётчики лотов, системные цены и первого администратора. Для полного запуска необходима отдельная инициализация этих записей.

### Игровые и финансовые сценарии

- `play_jackpot` возвращает результат, если победителей нет, но обрывается после получения фонда при найденных победителях. Выплата jackpot в этом срезе не завершена.
- Есть создание Stars invoice, обработчик `successful_payment` и сервис покупки билета за Stars. Не найден обработчик `pre_checkout_query`, необходимый для подтверждения checkout; идемпотентность начисления по идентификатору платежа также не показана.
- TON-пополнение передаётся клиентом в `/user/history`; сервер изменяет баланс по переданным данным. Независимое подтверждение платежа в блокчейне в этой реализации не показано.
- Для внешних соцсетей, кроме Telegram, endpoint фиксирует выполнение задания, а не проверяет подписку у провайдера. Защита от повторного получения бонуса требует доработки.
- В изменении номера, активации и получении выигрыша передаётся ID билета, но проверка владельца в этих сценариях не показана. Это нужно исправить перед публичным запуском.
- Покупка, изменение баланса и распределение фонда выполняются через несколько транзакций. Конкурентный доступ, идемпотентность и восстановление после сбоя требуют отдельной проверки.

### Окружение

- Compose описывает API, бота, Redis, Celery и consumer, но не PostgreSQL и RabbitMQ. Их адреса должны быть предоставлены отдельно. Полный Compose-стек не проверен.
- CORS middleware появился; список origin содержит исторические домены и не включает локальную админ-панель на порту 3001. Для её работы нужен согласованный origin или reverse proxy.
- Frontend сохраняет исторические TON manifest URL и счётчик Яндекс Метрики. Их актуальность не проверялась.
- Версии зависимостей исторические; аудит и обновление перед новым публичным развёртыванием остаются отдельной работой.

- Я восстановил стандартную проверку TLS-сертификата при проверке подписки Telegram.

- Я удалил отслеживаемые Python-кэши и `.DS_Store`, обновил README, инструкцию запуска, карточку проекта и шаблоны настроек.

**Перед повторным запуском мне нужно заменить опубликованные токены, ключи и пароли из старого `.env-prod` и кода.** Удаление текущих файлов не удаляет значения из Git-истории. Даже очистка Git-истории не отзывает опубликованные значения: перед запуском мне нужно выпустить новые секреты.
